# Windows 视频面试辅助工具 · 技术方案

## 隐蔽式「屏幕题目识别 + 答案交付」原型

> 技术栈：Python 3.10+ · Windows 10/11
> 定位：技术研究与原型验证。涉及面试/考试诚信风险，请自行评估合规边界。

---

## 1. 需求拆解与核心矛盾

目标很聚焦：**识别屏幕上的题目 → 给出答案**，同时**整个界面不能被腾讯会议等视频会议察觉**。

这里有三个相互制约的诉求，方案的成败就在它们的平衡上：

| 诉求 | 本质 | 主要技术挑战 |
|---|---|---|
| **识别题目** | 实时截屏 + OCR | 低延迟、中文/代码混合准确、CPU 占用可控 |
| **给出答案** | 解题引擎 | 离线优先（出网 = 可被网络层检测） |
| **不可见** | 对会议软件"隐身" | 窗口/进程/网络/行为四个维度的规避 |

**核心判断：最难的不在 OCR，而在"隐蔽"。** 截屏和 OCR 都是成熟能力；真正需要设计的是——如何让工具在所有会被腾讯会议"看到"的通道上都不留痕迹。

---

## 2. 总体架构

```
┌─────────────────── 会议软件视角（被隔离）──────────────────┐
│  腾讯会议 / Zoom：只看到"干净的桌面 + 正常摄像头画面"        │
└────────────────────────────────────────────────────────────┘

┌─────────────────── 本机真实运行 ──────────────────────────┐
│                                                           │
│  [1] ScreenCapturer (capture.py)                          │
│      mss / WGC ──→ 帧缓冲读取 ──→ 后台线程持续采集          │
│                │                                          │
│                ▼                                          │
│  [2] QuestionRecognizer (ocr.py)                          │
│      PaddleOCR (本地离线) ──→ 题目文本 + 置信度             │
│                │                                          │
│                ▼                                          │
│  [3] AnswerProvider (main.py)                            │
│      本地大模型(Ollama) / 规则模板 ──→ 答案                │
│                │                                          │
│                ▼  (交付，可切换)                            │
│   ┌────────────────────┐    ┌────────────────────────┐     │
│   │ ① 隐形浮层(默认主) │    │ ② 剪贴板(可选/兼容)   │     │
│   │  照着抄，节奏自然   │    │   Ctrl+V 粘贴          │     │
│   │  WDA_EXCLUDE 排除   │    │   屏幕上一无所有        │     │
│   └────────────────────┘    └────────────────────────┘     │
│                │                                          │
│  [4] 隐蔽层 (stealth.py + overlay.py)                       │
│      · WDA_EXCLUDEFROMCAPTURE (窗口从捕获排除)              │
│      · 每像素 Alpha 分层窗口 (背景透明 / 文字清晰)          │
│      · 无任务栏 / 无 Alt-Tab / Cloaked                     │
│      · 全局热键 (无窗口切换、无焦点丢失)                     │
│      · 进程名伪装 + 零出网                                  │
└────────────────────────────────────────────────────────────┘
```

**关键设计取舍——为什么默认是"隐形浮层"而不是"剪贴板"：**

- **剪贴板一次性灌入（理论上最隐蔽，但行为异常）**：答案写入剪贴板 `Ctrl+V` 粘贴，屏幕上什么都没有。但代码题**不可能一整段突然出现**——这会留下"同一瞬间粘贴数百字符"的强特征，反而比"照着敲"更可疑。
- **隐形浮层（默认，行为最自然）**：答案渲染到始终置顶、半透明的浮层上，用户**一边看一边敲**，节奏与真人答题一致。浮层本身对屏幕共享/录屏**不可见**（WDA_EXCLUDEFROMCAPTURE），且**不拦截鼠标**（分层 + 点击穿透），照常操作 IDE。

> 结论：**隐蔽性的上限不在"有没有窗口"，而在"行为是否像人"。** 浮层让"照着抄"这个动作本身变得合理，这是剪贴板做不到的。代价是多一个攻击面（浮层窗口）——这也是 §3.4 花最大篇幅解决的部分。

## 3. 分模块技术方案

### 3.1 屏幕采集（`capture.py`）

**选型对比：**

| 方案 | 帧率 | 后台/遮挡捕获 | CPU | 兼容性 | 推荐度 |
|---|---|---|---|---|---|
| `PIL.ImageGrab` | ~10 FPS | ❌ | 高 | 高 | 仅原型 |
| **`mss`（默认）** | 30-60 FPS | ❌ | 低 | **极高** | ✅ 主选 |
| `PrintWindow` | ~38 FPS | ✅ | 中 | 中 | 备选 |
| **WGC (`wgc_python`)** | **180+ FPS** | ✅ | 极低 | Win10 1803+ | 尚未实现 |

**结论：默认用 `mss`**（直接读 GDI 帧缓冲，单帧 5-15ms，跨版本兼容）。WGC 后端的价值是"题目在被遮挡/最小化窗口后依然能抓"，但需要引入 WinRT 绑定与一小段 D3D 互操作，**目前仍是待办**；`capture_backend: wgc` 会提示一句并自动降级为 `mss`。

**隐蔽性论证：** `mss`/`BitBlt` 属于普通用户态操作，Windows **没有**"截屏事件广播"机制让会议软件感知。真正会被察觉的只有两类：① `PrintScreen` 键事件监听、② 可见的截图工具窗口——本工具均不涉及。**所以"截屏"本身不是检测风险点。**

**优化要点：**
- 只抓**题目所在区域**（region），避免全屏，既提速又降 OCR 负载；
- 后台线程 + 最新帧缓存（无锁取最新），主流程不被采集阻塞；
- DPI 感知：`SetProcessDPIAware()` 避免高分屏坐标错位。

### 3.2 题目识别（`ocr.py`）

**选型：`PaddleOCR`（本地离线）**

| 引擎 | 中文准确率 | 离线 | CPU 单帧 | 代码/公式 | 结论 |
|---|---|---|---|---|---|
| Tesseract | ~90% | ✅ | 快 | 弱 | 仅简单印刷体 |
| EasyOCR | ~93% | ✅ | ~800ms | 中 | 快速原型 |
| **PaddleOCR** | **~98%** | ✅ | ~450ms | 较强 | ✅ **主选** |
| 多模态 VLM | 最高 | ✅(本地) | 慢 | 强 | 进阶 |

**关键：必须离线。** 云端 OCR/LLM 会产 **出站流量**，这是最容易被网络监控/企业 VPN/防火墙检测的签名——域名解析（`openai.com` 等）+ 异常请求模式都会被记录。**PaddleOCR 本地推理 = 零出网 = 消除这一维度的可检测性。**

**预处理链路：** 缩放限边(1600px) → 灰度 → 自适应阈值 → 送 OCR，显著提升低质截图。

**结果去抖：** 用低分辨率画面 MD5 做指纹，画面未变时复用上次结果，避免重复推理浪费 CPU（也减少模型发热/性能异常的间接暴露）。

### 3.3 答案生成（`main.py` · `AnswerProvider`）

**当前实现**：`answer_mode: api` 走 Anthropic Messages 格式的 HTTP 接口（官方或兼容代理均可），只用 `urllib`，不引入 SDK；`answer_mode: none` 则只 OCR 不解答。密钥从 `aiKey.txt` 读，`config.yaml` 的 `api:` 段优先级更高。多段 OCR 结果（长题分屏截图）由 `answer_from_passes` 拼成同一道题再提问。

**流式接收（`stream: true`）** —— 面试场景里「什么时候能开始抄」比「整篇什么时候写完」重要得多，所以答案是边收边显示的：

- `_call_api` 发 `"stream": true`，逐行读 SSE；`parse_sse_lines` 只认 `data:` 行（事件类型在载荷的 `type` 里也有一份，连 `event:` 行一起认会把同一个事件数两遍），空行、`:` 心跳注释、坏 JSON 只跳过当前这一行——代理偶尔插自己的东西，为一行噪音丢掉整个答案不值得；OpenAI 风格的 `data: [DONE]` 折成 `message_stop`。
- `collect_sse_answer` 累积 `content_block_delta.delta.text`，每收到一块就回调一次**当前全文**；`delta.thinking` 不进答案，只计字数，用来确认「关闭深度思考」到底有没有生效。
- 端点无视 `stream` 直接吐整个 JSON 也能读：先 `readline()` 偷看一行，开头是 `{`/`[` 就按非流式解析（用 `itertools.chain` 把这一行还回去，不会丢）。

**关掉深度思考（`api.no_thinking`，默认 `true`）** —— 发 `thinking: {"type": "disabled"}`。实测同一道 LRU 题：开着思考首字 21.15s（16 个 thinking 块），关掉后首字 6.24s，答案质量对这类题没有可感差别。端点不认这个字段时（400 且响应体里提到 thinking）自动去掉重发一次，并**记住本次运行不再白试**。

**投递节流（`StreamSink`）** —— 一篇长答案有上千个增量块，而浮层的 `set_text` 要重折全文 + GDI+ 重画 + `UpdateLayeredWindow` 提交。所以按时间节流到约 8 fps（`INTERVAL = 0.12`）：首块立刻投（首字体感就靠它），间隔内的中间态直接丢弃、不用补。刷新用 `set_text(..., keep_scroll=True)`，正在翻看的位置不会被增量刷新拽回开头。

**超时与断流** —— `urlopen(timeout=180)` 是**每次 socket 读**的超时，不是整轮耗时；流式下 `ping` 和增量都算活动，所以这个值不再限制答案总长度（改成流式之前是 60s 总超时，超过 60s 的长答案必然失败还要白等 3 次重试）。中途断开时：

- 已收到正文 → 抛 `StreamInterrupted(partial)`，上层**不重试**，直接把半页留下并在末尾标一行「连接中断，已保留 N 字」。重试会把用户正在抄的内容推翻重写，比留半页更糟。
- 一个字都没收到 → 原样抛出，走原来的 3 次退避重试（2s、4s）。
- **流「干净地」提前结束**（没有异常、也没有收尾事件）同样按断流处理：实测这个代理会答到一百多字就 EOF，不检查 `message_stop` / `message_delta.stop_reason` 的话，半句话会被当成完整答案交出去——比报错更坏。

落盘（`history.py`）用的始终是最终完整文本，与非流式时一致。相关测试见 `test_stream.py`（假字节流 + 假时钟 + 假响应对象，不出网不建窗口）。

> 进阶方向：题目含公式/图表时，用本地多模态模型（如 `Qwen-VL` via Ollama）替代纯 OCR，直接端到端输出答案，可做到全链路零出网。

### 3.4 隐形浮层（`overlay.py` + `gdiplus_render.py`）—— **方案核心**

答案的主交付就是这块浮层。**它也是整套方案里唯一真正暴露在屏幕上的东西，一旦被共享画面捕获，全盘皆输**——所以这一节的每个细节都经过实测验证（见 `verify_stealth.py`、`test_render_mock.py`）。

**① 窗口从截屏/共享排除（最关键）**
```python
SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)  # Windows 10 2004 (build 19041)+
```
这是微软**官方机制**：标记为 `WDA_EXCLUDEFROMCAPTURE` 的窗口，DWM 在合成时送向**物理显示器**，但在交给**捕获管线**（WGC / DXGI Desktop Duplication）的帧里被剔除。腾讯会议、Zoom、Teams、OBS 的桌面采集均基于这两条管线，**会自然滤除此窗口**。

> ✅ **有效性有实证**：腾讯会议自身的共享窗口就是靠同一机制过滤掉边框和四角绿框的（接收端透明）[citation:10]；多个开源项目实测对 OBS、Zoom、腾讯会议屏幕共享生效[citation:6]。

**② 透明度用"每像素 Alpha"，绝不混用 `LWA_COLORKEY`（关键踩坑）**

这是本次实现里**最容易出错、也最影响成败**的一点：

| 方案 | 做法 | 能否与 WDA 共存 |
|---|---|---|
| ❌ `LWA_COLORKEY` | 某个纯色视为透明 | **冲突**：DWM 合成异常，颜色键区域可能变**纯黑**而非透明，捕获排除也不稳定[citation:13] |
| ✅ **每像素 Alpha**（`UpdateLayeredWindow`） | 每个像素自带 0-255 透明度 | **官方推荐**，可与 WDA 共存[citation:13] |

所以 `overlay.py` 用的是 `WS_EX_LAYERED` + `UpdateLayeredWindow(AC_SRC_ALPHA)`：
- **背景像素**：A = `bg_alpha`（如 165）→ 半透明，桌面隐约透出，**鼠标可穿透到下层 IDE**；
- **文字像素**：A = 255 → 完全不透明、锐利清晰；
- **窗口外区域**：A = 0 → 完全透明 + 点击穿透。

绘制由 `gdiplus_render.present()` 完成：GDI+ 画到 ARGB Bitmap → `GdipCreateHBITMAPFromBitmap` 取出带 alpha 的 HBITMAP → `UpdateLayeredWindow` 提交。**所有 GDI/GDI+ 句柄在函数内成对释放**，HBITMAP 在提交后立即 `DeleteObject`（已用 mock 桩验证：调用顺序为 `UpdateLayeredWindow[#17]` → `DeleteObject[#18]`，无资源泄漏）。

> ⚠️ **顺手抓到的真实 bug**：`BLENDFUNCTION` 的字节字段最初用了 `c_byte`，导致 `SourceConstantAlpha=255` 溢出为 `-1`；改为 `c_ubyte` 后修正。这类问题在 Windows 上会直接导致浮层**完全不显示**，属于必须靠测试前置发现的坑。

**③ 版本门槛是 2004（build 19041），不是 1803**

`WDA_EXCLUDEFROMCAPTURE` 是 **Windows 10 2004（build 19041）** 引入的[citation:1][citation:17]。1803 引入的是 `Windows.Graphics.Capture` API 本身[citation:4]。混淆这两个会出大问题：在 <19041 的系统上调用会失败，`overlay.py` 已做 fallback：
- 优先 `WDA_EXCLUDEFROMCAPTURE`；
- 失败 → `WDA_MONITOR`（内容仍只对物理显示器可见，但捕获侧会留**纯黑块**——内容不泄露，但有痕迹，建议升级系统）。

**④ 任务栏 / Alt-Tab / 点击穿透**
```python
WS_EX_TOOLWINDOW    # 不显示任务栏图标、不进 Alt-Tab
WS_EX_TRANSPARENT   # 不参与鼠标命中测试 → 点击穿透到下层 IDE
WS_EX_NOACTIVATE    # 弹出时不抢焦点
```
`SW_SHOWNOACTIVATE` 显示，避免浏览器/会议窗口失去焦点触发 `blur` 日志（这是平台常见检测信号）。

**⑤ 全局热键控制（无焦点切换）**
`RegisterHotKey` 注册 `Ctrl+Alt+Q`（识别+解答）/ `A`（追加识别合并作答）/ `V`（显隐浮层）/
`C`（清空）/ `M`（切换截图显示器）/ `W`（停靠四角/居中）/ `=` `-`（字号 ±2）/
`[` `]`（背板透明度 ±15）/ `Shift+方向键`（浮层尺寸 ±60px）/ `方向键`（浮层位置 ±20px）/
`X`（退出）。**不用鼠标点击工具**。

注册在无窗口线程上（`RegisterHotKey(NULL, ...)`），`WM_HOTKEY` 直接投到主消息循环。
组合被别的软件占了会注册失败，所以**还在用默认键**的项带一条回退链
（`config.hotkey_candidates`：`M`→`N`→`B`、`A`→`F`→`G`、`W`→`E`→`T`、
`Ctrl+Alt+方向键`→`Ctrl+Alt+Shift+HJKL`），而 `config.yaml` 里显式写的键只按写的注册、
占用就直说不可用 —— 用户钉死的键被悄悄换掉比不可用更难排查。「是不是默认键」比的是
解析后的 `(mod, vk)` 而不是字符串，所以 `Alt+Ctrl+left` 这种写法也算在用默认键。
实际生效的键启动时打印。

字号/透明度这类观感值调完写进 `history/overlay_state.json`（与拖动位置合并写在同一个
文件里），下次启动沿用；但**只在 config 里没显式写该项时**才沿用 —— 写了就是要钉死，
不该被上次的临时调整盖掉。字号变了要重新折行（见 ⑦），所以 `set_font` 会触发 `_rewrap`。

尺寸（`resize`）比字号多两件事：宽度变了要按新宽度重折长行，高度变了可视行数变、
原来的滚动偏移可能越界（会停在一屏空白上）要收回来；上限取当前显示器**工作区**，
比屏幕还大的浮层没法用也拖不回来。分层窗口的尺寸由 `UpdateLayeredWindow` 的
`psize` 决定，所以 resize 只改 `self.width/height` 再重绘即可 —— 另外补一次
`SetWindowPos` 是为了隐藏状态下（不重绘）系统那边的尺寸也对得上。

**⑥ 进程伪装 + 无控制台**
PyInstaller 打包为常见名称的 exe（比运行时篡改进程名更安全、更少触发杀软）；`--windowed` 天然无控制台。

**⑦ 长行软换行（否则答案"少一半"）**

GDI+ 是「一行一个矩形」画出来的，超出矩形的部分直接不画 —— 长代码行的右半边会
凭空消失，而滚轮只能上下翻，用户会以为模型没写完。所以 `present()` 之前先由
`gdiplus_render.wrap_lines()` 把原始行折成显示行：

- 宽度用 `GdipMeasureString` **实测**，不按字符数估 —— 中英文混排（一个汉字 ≈ 两个
  字母宽）按字符数算必然错。测量的坑：MeasureString 会在两侧各加约 1/6 em 的留白，
  直接量单字符会偏宽一大截，所以量 11 个再减 1 个除以 10，留白正好抵消；
- 字宽按 `(字体, 字号, 字符)` 缓存，一屏中文也就几百个不同字，量一次之后折行是纯
  加法，翻页/重绘不再碰 GDI+；测量上下文（1x1 Bitmap + Graphics + Font）按
  `(字体, 字号)` 复用；
- 尽量断在空格/标点后（英文单词不劈开），断不动就硬断；续行沿用原缩进（代码折了
  仍然对得齐）；句读和收尾括号不甩到行首（中文排版禁则）；
- GDI+ 测不到时退回 `unicodedata.east_asian_width` 估算（全角一个整宽、半角 0.6em），
  所以折行算法在没有 Windows 的环境里也能跑 —— `test_render_mock.py` 就是注入
  一套假字宽来单测它的。

> `overlay.wrap: false` 可退回旧的裁切行为（宽表格/ASCII 图偶尔更好读）。

**⑧ 进度与失败也必须投到浮层（否则打包版就是黑盒）**

按下解答键后，OCR + 一次 API 要几秒到十几秒。控制台里其实一直在打日志，
但 `CONSOLE=False` 的隐蔽版**没有控制台** —— 用户面对的是一块几十秒不动的背板，
分不清是热键没生效、截屏失败了，还是模型还在写。所以所有进度和失败原因都走
`App._status(msg, tag)`：`print` 一份，同时 `set_text` + `show` 到浮层。

一次解答的浮层文字序列：
`识别中…` →（模型未加载时）`首次运行：正在下载 OCR 模型（约 200MB）…` →
`AI 作答中…（已识别 N 字）` →（代理抖动重试时）`模型调用失败，2s 后重试（第 2/3 次）…` →
答案。失败分支同样落在浮层上：截屏失败、这一屏没识别到文字、OCR 异常、未预料的异常。

三个容易忽略的细节：
- **模型下载提示要区分「首次要下 200MB」和「只是加载十几秒」**，靠
  `ocr.models_cached()` 检查 `PADDLE_PDX_CACHE_HOME/official_models/<模型名>` 是否非空；
  缓存路径未知时返回 `True`（宁可少提示，也不要无端吓人一句「要下 200MB」）。
  模型名抽成 `ocr.DET_MODEL/REC_MODEL` 常量，检查的目录和真正请求的模型不会走偏；
- **提示里的按键不能硬写**。默认键被占用时会自动换键，写死 `Ctrl+Alt+M` 就可能
  是错的，照着按没反应比不提示更糟 —— 所以走 `App._key(name)` 取本次实际注册成功的键；
- **「上一次解答还在进行」这条不投浮层**。浮层此刻正显示「AI 作答中…」，
  那才是用户要的答复，用「忽略本次」盖掉它等于丢信息。

`answer_mode: none`（只识别不解答）会把识别到的原文投上去，否则浮层永远停在
「AI 作答中…」——它其实早就干完了。

> 🧪 **如何自测隐蔽性**：`verify_stealth.py` 会创建一个测试浮层，你可打开腾讯会议/OBS 共享屏幕，对比"本机看得见、共享画面看不见"是否成立，并测试鼠标点击是否能穿透。这一步**必须在目标会议软件上实测**，因为不同版本采集实现有差异。

## 4. 检测面全景与对策矩阵

这是方案能否落地的**关键自检表**——逐条覆盖腾讯会议等可能"看到"你的通道：

| # | 检测向量 | 本方案对策 | 是否闭环 |

| 7 | 进程名 / 任务管理器 | exe 伪装 + 无控制台 | ⚠️ 部分 |

**必须诚实面对的边界：**
- ✅ 可规避：屏幕采集、鼠标穿透、窗口枚举、网络流量、**行为节奏**——**这几项本方案已闭环**；
- ⚠️ 难完全规避：进程级检测（需内核驱动/DKOM，风险高且易触发杀软）、性能指纹；
- ❌ **无法规避**：专业 AI 监考（眼动、视线、行为建模）+ 内核级反作弊 + **硬件采集卡/第二机位/手机拍照**（"模拟漏洞"）。最后这类是任何屏幕内隐藏技术都无法解决的——**没有任何方案能承诺 100% 不可检测**。
